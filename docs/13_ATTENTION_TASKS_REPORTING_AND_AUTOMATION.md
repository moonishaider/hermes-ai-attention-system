# Attention, Tasks, Reporting, and Automation

## Attention queue

A ranked, concise queue—not a firehose.

Each item includes:

- why it matters;
- context;
- urgency and impact;
- whether Syed must act;
- deadline;
- owner/waiting-on;
- evidence;
- confidence;
- suggested next action.

Ranking should learn from accepted/dismissed items but keep explicit rules visible.

## Context-switch handoff

When Syed switches domains, provide a short briefing:

- what changed since last active;
- unresolved commitments;
- blockers;
- people waiting;
- next three actions;
- new contradictions;
- meeting/calendar items.

## Open loops

Detect and track:

- promises by Syed;
- promises by others;
- unanswered questions;
- requested deliverables;
- blocked tasks;
- pending approvals;
- due dates;
- follow-ups without dates.

Avoid creating false tasks from speculative language. Low-confidence candidates go to Triage.

## Meeting intelligence

Before:

- relevant prior meetings;
- Slack/email context;
- open decisions;
- commitments;
- agenda/questions.

After:

- decisions;
- actions and owners;
- contradictions;
- commitments;
- risks;
- follow-up draft;
- source transcript citations.

Department meetings can be relevant even if Syed did not attend. Never state he attended unless evidence supports it.

## Project resumption

For an inactive project:

- last known objective;
- current state;
- latest relevant Codex/ChatGPT/source activity;
- completed work;
- blockers;
- unresolved decisions;
- files/repositories;
- next three actions.

## Daily Inside Success report

Inputs:

- company-context Codex work;
- company Slack evidence;
- company meetings;
- company tasks/status;
- approved manual additions.

Pipeline:

1. gather evidence;
2. exclude unrelated contexts;
3. classify completed/in-progress/blocked;
4. produce required format;
5. show sources and exact preview;
6. allow edits;
7. publish through fixed-channel wrapper after approval;
8. store report and result in audit log.

The report must not claim work merely because it appeared in a meeting or message.

## Automation discovery

Observe repeated workflows and propose:

- trigger;
- steps;
- frequency;
- time spent;
- potential automation;
- permissions required;
- failure risk;
- estimated savings;
- evidence occurrences.

Do not build/enable automatically. The user accepts only genuine, evidence-backed ideas.

## ROI meter

Track:

- commitments caught;
- missed-task prevention;
- briefings used;
- reports generated/approved;
- automation proposals accepted;
- time saved estimate;
- false positives;
- user corrections;
- monthly model/hosting cost.

Use transparent assumptions. The purpose is to identify whether the system is actually useful.

## Shopping research

Given a product need:

- clarify constraints from existing context where possible;
- search relevant stores;
- match exact model/specification;
- compare seller reliability, delivery, warranty, price, discounts, and total cart impact;
- cite current listings;
- avoid duplicate/near-identical results;
- prepare cart actions only within the permitted browser profile;
- never purchase automatically.

## GitHub evidence in attention and reporting

The attention engine may use recent relevant commits, pull requests, reviews, issues, failed checks, and repository changes as evidence. The Inside Success daily activity report may include Syed’s confirmed activity in accessible `inside-success` repositories, but it must avoid counting automated activity or other people’s work as Syed’s. Every generated item should link to immutable GitHub provenance.
